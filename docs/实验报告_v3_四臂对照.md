## 一、为什么要补这一轮

申请书要求「先实现**纯本地、纯云端**及规则协同三种模式」，并明确「**以同任务纯云端大模型为基线**」。
但 v1/v2 只有两条臂：`direct`（规则路由，实际 82% 的调用落在本地）和 `dot`。
**纯云端基线一直是缺的**，所以「协同相对纯云端到底如何」这个问题此前无法回答。

本轮补齐四臂（每臂 17 题 × 3 轮 = 51 次请求）：

| 臂 | 档位来源 |
|---|---|
| `local` | 强制本地（协同收益的下界） |
| `cloud` | 强制云端（**申请书的对照基准**） |
| `direct` | 规则整请求路由 |
| `dot` | 闸门 + 子任务级分配（主方案） |

## 二、三指标结果

| 臂 | 准确率（15 题计分 ×3） | p50 | p95 | 云端 token |
|---|---:|---:|---:|---:|
| `local` | 80.0%（36/45） | 1,528.1 ms | 8,803.6 ms | **0** |
| **`cloud`** | **100%（45/45）** | **759.0 ms** | **3,021.2 ms** | **6,551** |
| `direct` | 80.0%（36/45） | 1,137.9 ms | 2,898.2 ms | 2,603 |
| `dot` | **100%（45/45）** | 2,137.0 ms | 4,075.1 ms | 34,675 |

### 相比纯云端（本轮问题的直接答案）

| 指标 | 纯云端 | dot | 结论 |
|---|---:|---:|---|
| 任务性能 | 100% | 100% | **打平** |
| 完整响应时间 p50 | 759.0 ms | 2,137.0 ms | dot **慢 2.8 倍** |
| 完整响应时间 p95 | 3,021.2 ms | 4,075.1 ms | dot **慢 1.35 倍** |
| 云端 token 消耗 | 6,551 | 34,675 | dot **多 5.3 倍** |

**dot 在三个指标上都没有跑赢纯云端，准确率只是打平。**

---

## 三、v2 里那个「准确率优势」得到解释，且不能算数

v2 报告第六节曾披露：dot 100% vs direct 82.2% 存在混杂。本轮用纯云端臂把它拆开了：

- **纯云端也是 100%，与 dot 完全相同。**
- 而 `direct`（80%）与 `local`（80%）**完全一样** —— 因为规则路由把 51 次调用里的 42 次都判给了本地，direct 实质上≈纯本地。

所以：**dot 的 100% 来自「它的汇聚步骤在云端」，而不是来自「拆解」。** 云端臂全部走云端，同样 100%。
v2 那句「+17.8pp 准确率优势」到此可以确定地撤回——**它买到的就是云端本来就有的能力，而且多付了 5.3 倍 token。**

## 四、成本结构：dot 贵在 prompt，不在输出

| 臂 | 调用数 | prompt token | completion token | 单次输出 |
|---|---:|---:|---:|---:|
| `cloud` | 51 | **2,892** | 3,659 | 71.7 |
| `direct` | 51 | 3,558 | 4,988 | 97.8 |
| `local` | 51 | 3,699 | 6,225 | 122.1 |
| `dot` | 204 | **51,006** | 5,656 | 27.7 |

**dot 的 prompt token 是纯云端的 17.6 倍**（51,006 vs 2,892）。拆开看：

| role / tier | 次数 | 均输出 | 说明 |
|---|---:|---:|---|
| `decomposer`/cloud | 36 | 70 tok | 每次带约 600 token 的 few-shot 前缀 |
| `aggregator`/cloud | 36 | 11 tok | 输入要装下**全部**子任务答案 |
| `executor`/cloud | 9 | 228 tok | |
| `executor`/local | 123 | 6 tok | 瘦身生效：输出极短，且不计云端 token |

**v2 的「子任务瘦身」确实有效**（执行侧输出降到 6 token/次），但它治的是 completion 侧；dot 的成本大头在 **prompt 侧**——分解的固定 few-shot 前缀 + 汇聚的全量汇总。这两笔与题目难度无关，每进一次流水线就发生一次。

---

## 五、更根本的一点：这批题上，云端本来就非常便宜

纯云端 51 次请求只花 **6,551 token**，平均 **128 token/请求**。

因为题短、答案短（云端单次输出仅 71.7 token）。这意味着：

> 「云端 token 很贵、要用本地小模型省下来」这个前提，**在这批短问答上不成立**。
> 协同要省的那笔钱，天花板本身就很低（全部也就 6,551）。而为了省它，dot 先花掉了 34,675。

同样地，**本地在延迟上也不占优**：`local` 的 p50 是 1,528 ms，`cloud` 是 759 ms——本地慢一倍。
在 8GB 显存上跑 3B（约 67 tok/s）时，本地推理并没有比直连 API 快。端云协同「本地快、云端慢」的另一个前提，在这个硬件配置下也很弱。

## 六、方法学提醒：p95 在本设置下噪声很大

同一配置（dot、同一 17 题、3 轮）：

| 轮次 | p95 |
|---|---:|
| v2（`exp2-20261011`） | 2,765.9 ms |
| v3（`exp3-20261011`） | 4,075.1 ms |

**同一配置两次运行相差 47%。** 本地模型的推理耗时受显存热状态与调度影响明显，n=51 的 p95 落在尾部几个样本上，不稳定。

**因此本报告不基于单次 p95 的差异下结论**；上表按 p50 与 token 为主，p95 只作参考。后续若要报 p95，需要更多轮次或改用固定分位数的 bootstrap 区间。

## 七、局限

1. **题集偏向短问答**：17 题里 15 题是短算术/多步算术，答案是单个数字。这是 dot 最没有优势的场景，也是云端最便宜的场景。
2. **本地模型 3B / 8GB 显存**，DoT 论文用 Llama 3-8B。本地侧的延迟与质量都受此限制。
3. **无依赖图与并行执行**，故不能引用 DoT 论文 66% 的延迟降幅。
4. **闸门是启发式**，阈值未经扫描。
5. **分配器是阈值规则**，不是论文的 α-tree adapter。
6. **成本未计入本地算力**（电费/显卡折旧），口径按申请书「本地 token 不计入消耗」执行。

## 八、结论与下一步

**结论**：在当前实现与当前题集下，**dot 相对纯云端没有任何一项优势**——准确率打平，token 多 5.3 倍，延迟慢 1.35~2.8 倍。同时 `direct` 与 `local` 打平（80%），说明规则路由实质上退化成纯本地。

**这个结果把问题定位到了场景，而不只是实现**：

- 省 token 的空间 = 纯云端花掉的那部分。短问答上它只有 6,551，**天花板太低**；
- 本地要在延迟上赢，需要本地推理真的比 API 快——在 3B/8GB 上并不成立。

**因此协同有意义的方向是「云端 token 真正变大的场景」**，而这恰好是 v4 计划里被推迟的两个机制所针对的：

| 方向 | 为什么它能成立 |
|---|---|
| **长上下文 / 多轮任务** | 云端 token 随上下文线性增长，压缩才有可省的基数；同时 dot 的 prompt 开销也能被压缩摊薄 |
| **高重复 / 模板化请求** | 语义缓存命中后云端 token 归零，而 dot 的固定规划税也可被缓存吃掉 |
| **本地算力更强的部署**（实验室 16GB 机跑 7B/8B） | 本地延迟进入可与 API 竞争的区间，下沉才省时间 |

**建议的下一步（按优先级）**：

1. **换题集，而不是继续调 dot**。构造长上下文/多轮任务集（云端单请求 token 达到数千量级），在那种场景下重跑四臂。当前题集上做什么优化都是在低天花板下挪。
2. **给分解的 few-shot 前缀上 prompt cache**。它是逐字节固定的前缀，命中 DeepSeek 缓存后这 23,151 token 的分解开销可大幅下降——这是当前最直接的一笔。
3. **重估「拆解」的必要性**。既然纯云端 128 token/请求就能拿 100%，那么对短任务「不拆」才是最优策略；闸门已能拦住一部分，但拦下的请求仍在 dot 臂内。可以考虑把闸门阈值调激进，让它接近「短任务全部直答」。
