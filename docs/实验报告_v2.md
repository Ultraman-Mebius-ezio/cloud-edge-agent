## 一、结论摘要

同一批 17 题 × 3 轮（n = 51 次请求 / 每种模式）：

| 指标 | direct（整请求路由） | dot（闸门+子任务级分配） | 比值 |
|---|---|---|---|
| **云端 token 消耗** | 2,594 | 34,678 | 13.4× |
| **任务性能**（15 道计分题 ×3 轮） | 82.2%（37/45） | 100%（45/45） | +17.8pp |
| **完整响应时间** p50 | 1,218.9 ms | 1,978.4 ms | 1.62× |
| **完整响应时间** p95 | 4,661.5 ms | **2,765.9 ms** | **0.59×（dot 更快）** |
| SLM 使用率（分配器判定） | — | 97.4% | — |
| 子任务数中位数 | 0 | 3.0 | — |

**一句话**：dot 的 p95 已经反过来优于 direct，但云端 token 仍是 13.4 倍；准确率优势**存在混杂因素，不能直接归因于子任务级分配**（见第六节）。

## 二、v2 相对 v1 改了三处

| 改动 | 位置 | 为什么 |
|---|---|---|
| **补预路由闸门** | 新增 `src/gate.py`，接入 `cli.answer_dot` | v1 实测 dot 有一笔与题目难度无关的固定规划税（最低 842 云端 token/请求）。简单题与开放题不该进流水线 |
| **子任务输出瘦身** | `runner.PROMPT_HEADER` 加「只给结论或数值，最多一句话」 | v1 里汇聚占 dot 云端 token 的 32.9%，根因是本地子任务输出 600~1000 token |
| **题集补足多步题** | `evals/questions.txt` 新增 E 组 8 题 | v1 的多步题只有 4 道，而 direct 已拿到 85.7% 准确率——**拆解没有赢的空间**。DoT 面向多步推理，其 benchmark 上 CoT 只有 42%~80% |

闸门是**结构性规则**，不看题目难度、不看模型输出：纯算术 → 不拆；含顺序词 / ≥3 个已知量 / ≥2 个问句 / 超长 → 拆；开放性问题词 → 不拆。

## 三、v1 → v2：同一批题的改进幅度

只取两版共有的 9 道题（**最干净的对比，题集没变**）：

| | v1 dot | v2 dot | 变化 |
|---|---:|---:|---|
| 云端 token | 110,929 | 13,053 | **−88.2%** |
| 完整响应时间 p50 | 4,597.2 ms | 1,823.1 ms | **−60.3%** |
| 完整响应时间 p95 | 73,346.1 ms | 2,940.1 ms | **−96.0%** |

同批题上 direct 两版基本不变（token 2,598 → 2,594，p50 624 → 746 ms），说明改进来自 dot 侧而非环境漂移。

**结论**：v1 报告的「42.7 倍 token、13.2 倍 p95」绝大部分是**缺闸门 + 子任务话痨**造成的实现代价，不是范式的固有成本。

## 四、闸门效果

| 去向 | 请求数 | 云端 token | 耗时合计 |
|---|---:|---:|---:|
| 闸门拦下 → 整请求直答 | 15 | 2,327 | 16.9 s |
| 放行 → 分解流水线 | 87 | 34,945 | 153.3 s |

拦下理由分布：`短且无多步信号`×9、`开放性问题（分析）`×3、`开放性问题（解释）`×3。

闸门拦下的正是 v1 里 dot 亏得最惨的两类：单步算术（"24 个苹果吃掉 7 个"，v1 是 2,563 ms / 865 token）与开放题（v1 单请求 64~70 秒、9k~20k token）。拦住后这 15 次请求合计只花 2,327 token。

## 五、规划开销现在占了 91.7%

| 项目 | 云端 token | 调用次数 | 耗时合计 |
|---|---:|---:|---:|
| 规划（分解 + 汇聚） | **31,787（91.7%）** | 72 | 48.5 s |
| └ 分解 `decomposer` | 23,151 | 36 | 28.4 s |
| └ 汇聚 `aggregator` | 8,636 | 36 | 20.1 s |
| 执行（子任务） | 2,891 | 132 | 36.3 s |

瘦身见效了：执行侧云端 token 从 v1 的 57,193 掉到 2,891（**−94.9%**）。代价是**规划开销的占比反而升到 91.7%**——dot 的云端成本现在几乎全部是「拆分」与「汇总」本身。

这仍然指向同一个结论：**dot 的云端消耗由「是否进流水线」决定，与题目难度关系不大**。闸门是目前唯一有效的杠杆。

---

## 六、⚠️ 准确率优势的混杂因素（必须披露）

dot 45/45 = 100%，direct 37/45 = 82.2%。但这个差距**不能归因于「子任务级分配更准」**。

8 处失败全部落在 3 道多步题上，逐条核实调用档位：

| 题 | direct 的调用档位 | dot 的最终汇聚档位 |
|---|---|---|
| 一个班 45 人，3/5 是女生（错 3/3） | **local ×3** | cloud |
| 5 支笔 + 3 本本子（错 2/3） | **local ×3** | cloud |
| 往返平均速度（错 3/3） | **local ×3** | cloud |

**direct 把这三道多步题交给了本地 3B，而 dot 的最后一步（汇聚）永远在云端（36/36 次）。**

所以这个对比实际上混了两件事：
1. 拆不拆（子任务级分配）；
2. **最后一步落在云端还是本地**。

而 direct 之所以走本地，是因为 `allocator` 的规则只按「长度 / 开放词 / 纯算术」判定——多步短题既不长也不含开放词，于是落到默认本地。**这是规则路由器的已知短板**（DoT 论文里对标的 DataShunt 是用 LLM 判断查询复杂度，不是规则）。

> `src/cli.py` 的 `answer_direct` 注释里本来就写着「**绝不能当强基线**」——这次的数据正好印证了那句话。

**结论：本轮不能宣称 dot 更准。** 要拆开这个混杂，需要一个对照臂：**direct 强制把多步题送云端**。见第八节。

---

## 七、局限

1. **准确率对比有混杂**（第六节），本轮不可用于支持「dot 更准」。
2. **样本仍偏小**：15 道计分题 × 3 轮。direct 的 8 次失败集中在 3 道题上。
3. **模型规模远小于论文**：本机 8GB 显存只能用 3B，DoT 用 Llama 3-8B；分解质量与子任务粒度直接受此影响。
4. **无依赖图与并行执行**：DoT 的 66% 延迟降幅主要来自图并行，本项目未实现，**不能引用论文的延迟数字**。
5. **闸门是启发式**，阈值（顺序词表、≥3 个已知量）未经扫描调优；它在本题集上的判定全部合理，但不保证泛化。
6. **开放题无法自动评分**，2 道开放题被排除在准确率之外。

---

## 八、结论与下一步

**本轮确实改善了三指标中的两项**：
- p95 反超 direct（0.59×）——机制是 direct 会把多步题交给本地 3B 而让输出发散拖长尾；dot 把问题切成短子任务，尾延迟被压平。
- 云端 token 从 v1 的 42.7 倍降到 13.4 倍（同批题上 −88.2%）。

**仍未解决的是成本结构**：dot 的云端 token 有 91.7% 花在拆分与汇总上。这不是靠调 prompt 能解决的，需要动结构。

下一步按优先级：

1. **补对照臂：direct 的多步题强制走云端**。这是拆开第六节混杂的唯一办法，也是让准确率结论站得住的前提。实现上只需给 `answer_direct` 加一个「多步题判 cloud」的规则分支（复用 `gate.should_decompose`），半天可完成。
2. **降低分解的固定成本**。分解 36 次花 23,151 token（约 643/次），其中 few-shot 示例是固定前缀——把它逐字节固定在最前面，吃 DeepSeek 的 prompt cache。
3. **重估拆解粒度**。子任务中位数 3，多数题只拆 3 步；可以试 MAX_SUBTASKS=4~6 的扫描，看「更少但更准的子任务」能否同时压成本。
4. 之后才谈依赖图与并行。

## 九、长上下文场景（LongBench，2026-10-12 补）

### 9.1 为什么补这一节

第 1~8 节的题集全是短问答，纯云端只要 **128 token/请求**——「用协同省云端 token」的天花板本身就极低。
所以换到**云端 token 真正变大**的场景重测：长上下文问答。

- 数据：**LongBench**（清华 THUDM，MIT 许可）中文子集 `dureader`（多文档问答）+ `multifieldqa_zh`（单文档问答）
- 选样：各取 4 条、context ≤ 14,000 字，共 **8 条**（2,946 ~ 13,873 字），固定写入 `evals/longctx_items.jsonl`
- 规模：8 条 × 4 臂 × 3 轮 = **96 次请求**（n = 24/臂）
- 运行：`python -m evals.longctx run exp4-longctx-20261012 3`

### 9.2 三指标结果

| 臂 | p50 | p95 | 云端 token | 每请求 token | 质量：包含命中 | 质量：字符 F1 |
|---|---:|---:|---:|---:|---:|---:|
| `cloud` | **731.3 ms** | 1,396.8 ms | **141,591** | **5,900** | 25%（6/24） | 0.508 |
| `direct` | 657.8 ms | 1,606.1 ms | 141,617 | 5,901 | 25% | 0.513 |
| `local` | 5,124.4 ms | 10,340.4 ms | 0 | 0 | 25% | **0.561** |
| `dot` | 10,224.0 ms | 23,225.4 ms | 334,178 | 13,924 | 25% | 0.546 |

**相比纯云端**：dot 的云端 token 是 **2.36 倍**、p50 是 **14.0 倍**、质量打平。

### 9.3 关键发现

**① 换场景的方向是对的：云端 token 确实变大了 46 倍**

纯云端从短问答的 128 token/请求涨到长上下文的 **5,900 token/请求**。可省的基数终于变大了。

**② 但 dot 依然全输，而且放大倍数更大**

dot 的 prompt token 是 **860,161**，纯云端 140,718 —— **6.1 倍**。根因是**架构性的**：

| | 调用次数 | 每次 prompt |
|---|---:|---:|
| `cloud` | 24 | 5,863 token |
| `dot` | **141** | 6,100 token |

dot 每次调用的 prompt 与纯云端相当，但它**把同一段 context 重发了 5.9 倍**（分解带 context、每个子任务各带一份、汇聚再带全部答案）。**上下文越长，这个乘性放大越致命**——这是本次实验最值得记下的一条结构性问题。

**③ 规划开销占了 dot 云端 token 的 90.7%**

规划（分解 + 汇聚）303,219 token / 48 次调用，执行（子任务）仅 30,959 token / 93 次。dot 的云端成本几乎全是「拆分」和「汇总」本身，而且两者都要吃下整段长上下文。

**④ 规则路由在长上下文上退化成纯云端**

`direct` 的云端 token（141,617）与 `cloud`（141,591）几乎完全相同——因为长题干触发了 allocator 的「长文本(>60 字) → cloud」规则，全部被判上云。**规则路由在长上下文场景没有独立价值**，这两个臂实际上是同一个。

**⑤ 本地在长上下文上延迟崩了，质量也没赢**

`local` 的 p50 为 5,124 ms，是纯云端的 **7.0 倍**；质量上没有优势（F1 0.561 略高，但包含命中率相同，见下方的指标警示）。

### 9.4 指标警示：本节的质量数字不能细读

- **包含判定对长 gold 不适用**。`dureader` 的标准答案本身就是几百字长的段落，摘要式回答不可能逐字包含；而 `multifieldqa_zh-2` 标准答案是「人民币57081.86元。」，模型答「57081.86元。」语义正确却判为未命中。**四臂同为 25% 有指标饱和的成分，不能据此说四臂质量等价。**
- **字符 F1 偏向啰嗦答案**。它与长 gold 的召回率随回答变长而升高，所以本地/ dot 的 F1 略高**很可能是伪影**，不是真的更准。
- 结论：**本节只能支撑「四臂质量没有拉开明显差距」这一弱结论**，不足以排序。要排序需要 LongBench 官方指标（dureader 用 Rouge-L、multifieldqa_zh 用 F1），尚未实现。

### 9.5 这一节说明了什么

**长上下文确实把云端 token 放大了 46 倍——方向是对的；但当前架构吃不到这个红利。**

dot 的设计里，context 会在分解、每个子任务、汇聚三处被重复携带，放大是**乘性**的，context 越长越糟。
要吃到长上下文的红利，必须先实现 **上下文压缩**（把 context 压一次，各环节共用压缩版）——而这正是 v4 计划里被推迟的机制。

**结论：长上下文场景同样没有证明协同的优越性，但它精确定位了缺失的那个机制。**
