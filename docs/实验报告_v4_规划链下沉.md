# 端云协同原型 · 规划链下沉实验报告 v4

日期：2026-10-12 ｜ run_id：`exp3`、`exp5-localplan`、`exp6-localdec`、`exp4-longctx`、`exp7-ctx-localplan`

> 前作：`实验报告_v1.md`、`实验报告_v2.md`（第九节含长上下文）、`实验报告_v3_四臂对照.md`
> **本报告的结论是「没有拿到可用优势」，不是「dot 赢了」。第七节说明为什么。**

---

## 一、动机

v2/v3 把问题定位得很准，两次都指向同一处：

- 短问答：dot 的云端 token 有 **91.7%** 是规划开销（分解 + 汇聚）
- 长上下文：规划占 **90.7%**，且 dot 把同一段 context 重发 **5.9 倍**

所以本轮只做一件事：**把规划链下沉到本地**。

---

## 二、新增机制：规划链档位可配置

`src/config.py` 新增两个一等配置项，`planner.py` / `aggregator.py` 实时读取：

| 配置 | 取值 | 作用 |
|---|---|---|
| `PLANNER_TIER` | `cloud`（默认）/ `local` | 分解由谁执行 |
| `AGGREGATOR_TIER` | `cloud`（默认）/ `local` | 汇聚由谁执行 |

这不是调参开关，而是 DoT §3「原始查询只在边缘模型上做分解和分配」的原意——
规划链是端云协同里最该被下沉的一段。做成可配置才能量化「省下的 token」与
「掉掉的准确率」之间的权衡。

### 顺带修掉一个真问题

汇聚 prompt 的字符预算原来**恒定按本地窗口**卡（12,800 字符），理由是「云端未接入时
会降级到本地，不按本地窗口保护会超窗」。但云端可用时这个预算白丢子任务答案——
长上下文场景实测**每条请求要丢 4~5 条**。现改为按汇聚器实际档位取预算
（`_prompt_budget()`：云端档 48,000 / 本地档沿用本地窗口）。

> **但这个修复实测没有效果**：汇聚 prompt 依然约 6,100 token / 次（改前 6,096）。
> 原因是 prompt 的主体是「原始问题」本身（含 13k 字长上下文），不是子任务答案。
> **又一次撞上同一个结构问题：context 被重发。**

---

## 三、短问答：四配置权衡曲线

17 题 × 3 轮 = 51 次请求；计分 15 题（开放题除外）。

| 配置 | 云端 token | 准确率 | p50 | p95 |
|---|---:|---:|---:|---:|
| **纯云端（基线）** | **6,297** | **100%** | **707.6 ms** | 2,638.1 ms |
| dot：分解云端 + 汇聚云端 | 34,675 | 100% | 2,137.0 ms | 4,075.1 ms |
| dot：分解本地 + 汇聚云端 | 12,051 | 86.7% | 2,481.8 ms | 4,940.0 ms |
| dot：**分解本地 + 汇聚本地** | **2,848** | **75.6%** | 2,318.5 ms | 5,345.1 ms |

**dot 在末行第一次把云端 token 压到纯云端之下（0.45×）。** 但代价是准确率 100% → 75.6%。

### 准确率为什么掉——逐条可解释

失败的都是**最终组合推理**，不是子任务划分：

| 失败题 | 本地汇聚给出的答案 | 正确答案 | 错误类型 |
|---|---|---|---|
| 一桶油连桶共重 25kg，倒掉一半后 14kg，桶重？ | 11 千克 | 3 千克 | 忘了把油重翻倍 |
| 甲乙相距 360km，去 6h 回 4h，往返均速？ | 75 km/h | 72 km/h | 经典的「平均的平均」 |
| 一个班 45 人，3/5 是女生，多几人？ | 多 6 人 | 多 9 人 | 男生数算错 |
| 156 ÷ 12 | 12.916666… | 13 | 本地算术错（**该题被闸门拦下，与规划无关**） |

即：**本地 3B 能划分对子任务，但做不好把它们合起来。**

## 四、长上下文：同一模式，且绝对量依然很小

8 条 × 3 轮 = 24 次请求（LongBench `dureader` + `multifieldqa_zh`）。

| 配置 | 臂 | 云端 token | 命中率 | 字符 F1 | p50 | p95 |
|---|---|---:|---:|---:|---:|---:|
| 规划全云端 | cloud | 141,591 | 25% | 0.508 | 731.3 ms | 1,396.8 ms |
| 规划全云端 | dot | 334,178 | 25% | 0.546 | 10,224.0 ms | 23,225.4 ms |
| 规划全本地 | cloud | 141,748 | 25% | 0.518 | 950.5 ms | 1,956.4 ms |
| 规划全本地 | **dot** | **112,677** | 25% | 0.425 | 20,024.4 ms | 41,286.4 ms |

dot 的云端 token 从 334,178 降到 112,677（−66%），**低于纯云端的 141,748（0.79×）**。

**但规划下沉在这里只是小头**：dot 剩下的 112,677 里绝大部分是**云端执行的子任务各自携带整段长上下文**——52 次调用 × 每次约 6,000 token。本地规划省掉的是那两次规划调用，省不掉 context 的重发。

## 五、省下的 token 到底值多少

这是本轮最该被记住的一张表。把 token 换成钱：

| 场景 | 每次请求省下 | 全轮省下 | 折合人民币 |
|---|---:|---:|---:|
| 短问答（51 请求） | 68 token | 3,467 token | **约 0.35 分** |
| 长上下文（24 请求） | 1,211 token | 29,071 token | **约 2.9 分** |

按 DeepSeek 输入约 1 元/百万 token 估算。**两个场景省下的钱加一起不到 3 分。**

代价却是：
- 短问答：准确率 **−24.4 个百分点**、p50 **+1.6 秒**
- 长上下文：p50 **从 950 ms 涨到 20,024 ms（21 倍）**

**这笔交易不成立。** 不是因为方向错，而是因为**要被省的那个量本身太小**——
纯云端在短问答上只要 124 token/请求。这也是 v3 已经得出的结论，本轮把它量化了。

---

## 六、诚实的结论：没有拿到可用优势

按「准确率接近基线的前提下降低云端 token」这一申请书的验收口径，逐场景核对：

| 场景 | dot 云端 token | 是否赢 | 准确率是否接近基线 | 结论 |
|---|---:|---|---|---|
| 短问答 · 规划全本地 | 0.45× | ✅ 赢 | ❌ 75.6% vs 100% | **不成立** |
| 短问答 · 分解本地+汇聚云端 | 1.9× | ❌ 输 | ❌ 86.7% vs 100% | 不成立 |
| 长上下文 · 规划全本地 | 0.79× | ✅ 赢 | ⚠️ 打平（但 F1 最低） | **延迟 21 倍，不成立** |

**没有任何一个配置同时满足「token 低于纯云端」与「准确率接近基线」。**

需要说明的一点：本轮**没有**达到「dot 具备确定优势」这个目标。原因是可定位的，见下节。

---

## 七、真正的杠杆在哪

把三次实验的结论放在一起，瓶颈非常清楚：

**瓶颈是本地模型的能力，不是缺少机制。**

- 短问答上 dot 输，是因为本地 3B **汇聚**做不好（第四节逐条列了错误类型）
- 长上下文上 dot 输，是因为 context 重发，而这需要**上下文压缩**（未实现）
- 但即便压缩做完，**省下的绝对量仍然很小**——纯云端本来就只要 124 token/请求

所以按可能性排序，真正值得做的三件事是：

1. **换更强的本地模型**（实验室 16GB 机跑 7B/8B）。本轮所有准确率损失都来自 3B 的组合推理能力。本地模型一变强，第三节那条权衡曲线会整体右移——**这是最直接、最可能奏效的一步**，也是你们已有硬件条件支持的一步。
2. **换一个云端 token 真正昂贵的场景**。当前两个场景的纯云端消耗分别是 124 与 5,900 token/请求。只有后者量级以上的场景，「省 token」才有经济意义；而长上下文场景下 dot 又受制于 context 重发。所以需要**既长又重复**的场景（多轮 + 长历史），那里压缩与缓存能同时发力。
3. **上下文压缩 + 语义缓存**（v4 计划里被推迟的两项）。它们不是可选项，是上面第 2 条的前提。

**不建议继续做的**：在 3B 上继续调 dot 的规划链。本轮已经证明瓶颈不在这里。

---

## 八、局限

1. **本地模型 3B / 8GB 显存**，DoT 论文用 Llama 3-8B。本地侧的能力上限直接决定了本轮的全部准确率结论。
2. **长上下文质量指标不可细读**：包含判定对长 gold 不适用、字符 F1 偏向啰嗦答案（详见 `实验报告_v2.md` 第 9.4 节）。四臂同 25% 有指标饱和成分。
3. **p95 噪声大**：同配置两次运行 p95 可差 47%（v2 第 6 节）。本报告以 p50 与 token 为主。
4. **重复轮次的缓存放大**：同一 prompt 重跑 3 轮会吃到 DeepSeek 前缀缓存（长上下文场景 `direct` 命中率 96.9%），使后两轮的系统性偏快。四臂都受影响，但影响不均。
5. **口径提醒（本次会话新发现，尚未落到任何报告正文）**：`cloud_tokens` 按 prompt+completion 全额计，**含 DeepSeek 前缀缓存的命中部分**。实测命中率：短问答 dot 49.1%、长上下文 dot 63.2% / cloud 64.6% / direct 96.9%。若按**剔除缓存**的口径重算，短问答 dot/cloud 由 5.29× 降为 3.07×。**「云端 token 消耗」与「实际计费 token」是两个不同的量，报告应同时给出**——这正是申请书批评他人「口径不统一」的那件事，我们自己也要守住。
6. 分配器仍是阈值规则，非论文的 α-tree adapter。
