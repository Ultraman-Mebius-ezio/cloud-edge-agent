# 端云协同智能体原型

把用户的大任务**拆成子任务**，**逐个**判断该交给本地小模型还是云端大模型，
执行后汇总成答案。核心研究点是**子任务级分配**——这是相对「整请求路由」
（DataShunt 式）的改进所在，也是立项申请书研究内容 (2) 的落地。

一周实施计划见《原型一周实施计划.md》，接口契约见 `docs/接口冻结.md`。

---

## 快速开始

```bash
# 1. 依赖（已有 .venv 可跳过）
uv venv .venv
uv pip install litellm python-dotenv rich

# 2. 配置：复制模板，填入 DeepSeek key
cp .env.example .env      # 然后把 DEEPSEEK_API_KEY 填上

# 3. 本地模型（必须支持 tools；用 ollama show 确认）
ollama pull nanbeige4.2-3b-32k

# 4. 跑
PYTHONIOENCODING=utf-8 ./.venv/Scripts/python.exe -m src.cli
```

> **Windows 必须加 `PYTHONIOENCODING=utf-8`**，否则 GBK 控制台中文乱码。
> CLI 内部也对 stdout/stderr 做了 `reconfigure`，但外部重定向时仍需这个变量。

### 没有云端 key 也能跑

云端不可用时（`DEEPSEEK_API_KEY` 为空），`tier="cloud"` 的调用会**真的落到本地执行**，
并且 **`tier` 如实记为 `local`**——云端 token 绝不会被虚报。
被降级的事实另记在 `requested_tier` 字段，`--stats` 看板里能算出降级次数。

要改成严格失败（口径最纯净、但无 key 时 `dot` 模式不可用），把 `.env` 里
`CLOUD_FALLBACK_LOCAL` 设为 `0`。**做正式对照实验时应当接上真实云端。**

## 两种模式

| 模式 | 行为 | 用途 |
|---|---|---|
| `--mode direct` | 整请求判定走本地或云端，一次答完 | **对照基线**（对应文献里的 DataShunt 式整请求路由） |
| `--mode dot` | 分解 → 逐子任务分配 → 顺序执行 → 汇聚 | 主方案（默认） |

```bash
# 单次问答
PYTHONIOENCODING=utf-8 ./.venv/Scripts/python.exe -m src.cli \
    --mode dot --once "一个班 45 人，其中 3/5 是女生，女生比男生多几人？" --run-id exp1

# 指标看板
PYTHONIOENCODING=utf-8 ./.venv/Scripts/python.exe -m src.cli --stats --run-id exp1
```

**全部参数**：`--mode {direct,dot}` / `--once "问题"` / `--stats` / `--run-id ID` /
`--no-warmup` / `--db PATH`。

> `direct` 模式的路由是**规则路由**（复用 `allocator` 的阈值规则），
> **不是训练出来的路由器**。报告里不能把它当作强基线——它是同赛道的对照臂。

## 三指标口径

| 指标 | 定义 | 采集点 |
|---|---|---|
| **云端 token 消耗** | Σ(`tier=cloud` 的 `prompt_tokens + completion_tokens`)，**含分解、汇聚、失败与重试的每一次尝试** | 客户端埋点，落在 `calls` 表 |
| **完整响应时间** | 收到请求 → 最终结果返回，**含本地推理** | **请求级**，落在 `tasks` 表；报中位数 + P95 |
| **SLM 使用率** | 走 `local` 的子任务数 / 总子任务数 | 由执行结果的实际档位统计 |

**规划开销单独报告**：`role IN ('decomposer','aggregator')` 的 token 与耗时单独聚合。
DoT 论文没有把这笔开销单独计量，正文也没讨论「拆解本身值不值」——**这是本项目可写的点**。

> ⚠️ 「完整响应时间」是**请求级**量纲。拿 `calls` 表按调用算 P95 会把
> 拆成 5 次调用的请求当成 5 个样本，分位数被系统性地压低。
> 看板表 1 走的是 `tasks` 表，表 3 才是调用级明细，不要混用。

### 核心工程原则：唯一调用出口

**所有 LLM 调用必须经过 `llm_client.call_llm()`，没有例外。**

申请书要求「云端 token 累计所有 API 调用的输入与输出（含规划、校验、重试）」。
流水线把调用点从 1 个变成 k+2 个，绕过出口的概率大幅上升；
**只要有一处绕过，指标就是错的，而且不报错、只会静默偏低**——
等发现时实验要全部重跑。

因此：落库发生在 `call_llm` **内部**，调用方无法「忘记」记录；
失败调用也落库（`error` 字段）；重试的每一次尝试独立落一行
（失败那次的 prompt token 也是真花了钱的）。

## 实测结论（本机：RTX 5060 Laptop 8GB / Ollama / Python 3.11.2）

这些数字决定了代码里几个「反直觉」的设计，改动前请先读：

### ① `num_ctx` 拐点在 16384

| num_ctx | 4096 | 8192 | 12288 | **16384** | 24576 | 32768 |
|---|---|---|---|---|---|---|
| tok/s | 70.6 | 71.0 | 71.1 | **71.1** | 21.2 | 10.7 |

`num_ctx=32768` 在 8GB 卡上会挤爆显存（KV cache 3.4 GiB），**速度掉 6.6 倍**，
而且多出来的窗口根本用不满。故 `.env` 里设为 **16384**，
超出部分由 `runner` 的**前置答案预算截断**兜底（被截断的结果标 `dropped_context`）。

### ② sm_120 冷加载会偶发 CUDA 初始化失败

`RTX 5060 Laptop` 首次加载模型时偶发
`CUDA error: shared object initialization failed`（退出码 `0xc0000409`），
Ollama 自己第二次加载就成功（`%LOCALAPPDATA%\Ollama\server.log` 可见
`Load failed` → 紧随其后成功）。

因此 `call_llm` 带**有界重试**，且 **`warmup` 必须带重试**——
否则这个崩溃会被算进正式测量的 P95 里。

### ③ litellm 的 `num_ctx` / `think` 必须走顶层 kwargs

它们是本地模型的受控变量（`think` 开关实测影响 15 倍输出 token）。
**不要改用 `extra_body`**：实测那会把整个 `options` 对象**替换**掉，
连 `temperature` / `seed` 一起抹掉，且不报错。
验证脚本见 `notes/_probe_litellm_body.py`。

### ④ 固定项（改动需全员同步）

| 项 | 值 | 位置 |
|---|---|---|
| `temperature` | `0.0` | `.env` |
| `seed` | `42` | `.env` |
| 本地 `num_ctx` | `16384` | `.env` |
| 本地 `think` | `0`（关） | `.env` |

> `think` 影响极大：同一道题 `think=OFF` 输出 76 token / 3.2s 且答对；
> `think=ON` 输出 **1176 token** / 19.5s 且答案发散。**必须固定并在报告中写明。**
