## 0. 三条红线（违反则指标失真，且不报错）

1. **所有 LLM 调用必须走 `llm_client.call_llm()`**。流水线把调用点从 1 个变成 k+2 个，
   绕过的概率很高；一旦绕过，云端 token **静默偏低**，等发现时实验全部重跑。
2. **失败调用也要落库**——已在 `call_llm` 内部完成，调用方无需操心，但也**不要重试时自己吞掉异常**。
3. **不许自己数 token**。一律以 `usage` 为准。`LLMResult.usage_missing` 为真时必须让告警可见。

**除此之外还有一条**：`role` 必须在 `llm_client.ROLES` 里登记，否则 `call_llm` 直接抛
`ValueError`（这是故意的，防止指标里冒出计划外的分组名）。

### `src/llm_client.py`

```python
ROLES = ("decomposer", "executor", "aggregator", "warmup")

call_llm(
    *,
    messages: Sequence[dict],   # OpenAI 格式
    role: str,                  # 必须在 ROLES 里
    tier: str = "local",        # "local" | "cloud"   ← 这是「请求」档位
    strategy: str = "dot",      # "dot" | "direct" | "warmup" | "smoke"
    task_id: str = "",
    run_id: str = "default",
    tools=None,
    stream: bool = False,
    on_delta: Callable[[str], None] | None = None,
    retries: int = 0,           # 瞬时故障重试次数（每次尝试独立落库）
    **overrides,
) -> LLMResult
```

`LLMResult` 关键字段：

```python
text, tool_calls, reasoning
prompt_tokens, completion_tokens, cache_hit_tokens
latency_ms, ttft_ms, call_id
tier            # 实际执行的档位（降级后 = "local"）
requested_tier  # 请求的档位
fell_back       # property: requested_tier != tier
usage_missing   # True = token 没拿到，指标不可信
error           # None 表示成功
```

**降级语义（重要）**：云端 key 没配且 `CLOUD_FALLBACK_LOCAL=1` 时，`tier="cloud"` 的调用
会**真的在本地跑**，此时 `tier` 记 `"local"`、`requested_tier` 记 `"cloud"`。
所以**云端 token 绝不会被虚报**——本地跑的就是 0 云端 token。
调用方**不需要**为此写任何特殊分支，但要会在展示时用 `fell_back` 说明「本次被降级」。

`warmup(tier="local", rounds=1) -> float` —— 预热，内部已带重试。

### `src/metrics.py`

```python
metrics.record(CallRecord(...))          # call_llm 内部调用，业务代码不要直接调
metrics.record_task(TaskRecord(...))     # ★ 一次用户请求写一行，CLI 负责调用

TaskRecord(
    strategy, task_id="", run_id="default", question="", answer="",
    n_subtasks=0, n_local=0, n_local_planned=0, total_ms=0.0, cloud_tokens=0,
    plan_ms=0.0, exec_ms=0.0, error=None,
)

metrics.summary(run_id, include_aux=False)        # 按 strategy 汇总「调用级」
metrics.task_stats(run_id)                        # ★ 请求级：p50/p95、云端token、SLM率
metrics.role_summary(run_id, strategy=None, include_aux=False)
metrics.plan_overhead(run_id, strategy="dot")     # 分解+汇聚 vs 执行，单独拆开
metrics.percentile(values, p)                     # 线性插值分位数
```

**`task_stats` 的 SLM 使用率返回两个字段，别混用**：

| 字段 | 含义 | 什么时候看 |
|---|---|---|
| `slm_ratio_planned` | 分配器**判定**给本地的占比（池化 Σn_local_planned/Σn_subtasks） | **报告里引用这个** |
| `slm_ratio_actual` | **实际**在本地跑的占比（池化 Σn_local/Σn_subtasks） | 诊断用；云端不可用时恒为 100% |

两者都必须是**池化**的计数比，**不是「每条请求比值的算术平均」**——
子任务数不等时两者能差 26 个百分点（2 子任务/2 本地 与 8 子任务/1 本地：
平均 0.562 vs 池化 0.300）。planner 的子任务数本来就随问题在 2~8 之间变，
所以这个分叉必然踩到。

**`role_summary` / `plan_overhead` 默认剔除 warmup/smoke**，与 `summary()` 同口径；
要原始明细传 `include_aux=True`。算规划开销时 `strategy="dot"`——同一个 run_id 下
通常还跑过 direct，不锁策略会把 direct 那一发 executor 算进 dot 的执行开销。

**量纲提醒**：「完整响应时间」是**请求级**的，只能从 `tasks` 表算（`task_stats`）。
拿 `calls` 表按 strategy 算 P95 会把拆成 5 次调用的请求当成 5 个样本 → 分位数被压低。

## 2. 待实现的五个模块

统一约定：`from src import xxx`；中文 docstring，解释**为什么**而不只是**做什么**；
**不许新增第三方依赖**（只用标准库 + 已有的 litellm/dotenv/rich）。

### `src/planner.py`

```python
def decompose(question: str, *, task_id: str = "", run_id: str = "default") -> list[str]
```

- 一次 `call_llm(role="decomposer", tier="cloud", strategy="dot", retries=2)`。
- 提示词按 DoT 附录 C.1 改写为**中文**（原文是英文 + 8 个英文示例，中文场景必须重写示例）：
  - 指令：把问题拆成若干个「可独立求解」的步骤，每行一个，以编号开头。
  - 附 **2–3 个中文 few-shot 示例**（含一道多步数学题、一道需要比较的问题）。
  - 明确要求：**不要复述题干**，不要输出解释文字。（实测 3B 会产出复述题干的伪子任务）
- **解析容错（三层降级）**，按顺序尝试：
  1. 按 `^\s*\d+[.、)）]` 抽行；
  2. 抽不到 → 按换行切分，行首若有 `-`/`*`/`•` 等符号去掉；
  3. 还不行 → 返回 `[question]`（退化为不拆，**这是合法结果，不是错误**）。
- 每条子任务去掉首尾空白与 markdown 强调符（`*`, `` ` ``, `#`）。过滤空行。
- 子任务数上限 **8**（超出截断并在 stderr 告警）。少于 2 条时也返回 `[question]`。
- 云端调用失败（`result.error` 非空）→ 返回 `[question]`，并把 error 打到 stderr。
- 把 `result.text` 原样保留着方便排查——建议 `logging` 或 stderr 打印**截断到 500 字**。

### `src/allocator.py`

```python
def allocate(subtasks: list[str]) -> list[str]        # 返回等长的 "local"|"cloud"
def allocate_one(text: str) -> str
def explain(subtasks: list[str], tiers: list[str]) -> list[str]   # 给人看的判定理由
```

**纯规则，零 LLM 调用**（这是设计而不是省事：DoT 的 adapter 需要先造训练数据，
论文里不训练时 P3 只有 15%，所以 v4 用阈值规则并如实报告）。规则 v1：

| 条件（按优先级） | 判定 | 理由文案 |
|---|---|---|
| 文本长度 > `60` 字符 | cloud | `长文本(>60字)` |
| 命中开放词：说明/解释/分析/比较/论述/评价/为什么/原因/设计/证明/推理/权衡/优缺点 | cloud | `开放性问题(<词>)` |
| 纯算术（只含数字与 `+ - * / ( ) = ？? 的多少` 及空白，且有数字） | local | `纯算术` |
| 其余 | local | `默认本地` |

- 阈值与词表定义为**模块级常量**（`LONG_TEXT_CHARS`、`OPEN_ENDED_WORDS`），便于以后调参/扫描。
- `explain` 返回等长列表，给 CLI 展示用。

### `src/runner.py`

```python
@dataclass
class SubtaskResult:
    index: int
    text: str
    tier: str            # 实际执行档位（降级后为 "local"）
    requested_tier: str  # allocator 分配的档位
    answer: str
    prompt_tokens: int = 0
    completion_tokens: int = 0
    latency_ms: float = 0.0
    dropped_context: bool = False   # 本次是否因预算触发了前置答案截断
    error: str | None = None

def run(subtasks, tiers, *, question, task_id="", run_id="default") -> list[SubtaskResult]
```

- **顺序执行**（v4 明确不做依赖图与并行）。第 i 个的 prompt 带上 **0..i-1 全部已完成的答案**
  —— 这是 v4 的简化，DoT 原文是「只带直接前置依赖」，报告里要写明差别。
- 每次 `call_llm(role="executor", tier=tiers[i], strategy="dot", retries=2)`。
- **子任务 prompt 结构**：
  ```
  你是端云协同系统里的执行器。请只回答下面这一个子任务，不要复述整个问题。

  【原始问题】{question}

  【此前已完成的子任务与答案】
  1. {subtask} → {answer}
  ...
  【当前子任务】{subtask}
  ```
- **预算控制（必须实现，不许省略）**：用**历次调用回报的真实 token 数**做精确预算——
  每个 `SubtaskResult.completion_tokens` 就是该答案的实际 token 数，加上问题与模板的
  固定开销（用第一次调用回报的 `prompt_tokens` 减去当时前置答案的 token 数估算，或保守取常数）。
  若「固定开销 + 所有前置答案 token + 当前子任务」超过 `config.local_prompt_budget()`：
  **从最早的答案开始丢**，直到放得下，并把这些结果标 `dropped_context=True`，同时向 stderr 告警。
  - 只对 `tier=="local"` 的调用做这个预算（本地窗口是硬约束）；cloud 仍然带上全部前置答案。
- 单个子任务失败（`result.error`）不中断整体：该条 `answer=""`、`error` 记下，**继续跑后面的**。
- 每个子任务执行前用 `rich`（若在 TTY）或 print 打一行进度：`[3/5] tier=local 31.2s 正在执行…`

### `src/aggregator.py`

```python
def aggregate(question: str, results: list[SubtaskResult], *,
              task_id: str = "", run_id: str = "default") -> str
```

- `call_llm(role="aggregator", tier="cloud", strategy="dot", retries=2)`。
- prompt：原始问题 + 各子任务的「子任务 → 答案」清单 + 要求输出**面向用户的最终答案**，
  不要罗列过程。注明哪些子任务失败/无答案，让模型自己决定怎么处理。
- 全部子任务都失败 → **不调用 LLM**，直接返回一句说明（省一次必然无效的云端调用，也避免污染 token 统计）。
- 汇聚调用本身失败 → 降级返回「子任务答案的拼接」，并在末尾附告警行。

### `src/cli.py`

命令行入口，`python -m src.cli`。

```
--mode {direct,dot}   default: dot        direct = 整请求路由（对照基线）
--once "问题"          单次问答后退出（不做交互）
--stats               只打印指标看板后退出
--run-id ID           指定实验批次号；不指定则自动生成，如 run-20261002-2130
--no-warmup           跳过预热（默认会预热）
--db PATH             覆盖 metrics.db 路径
```

```python
def answer_direct(question, task_id, run_id) -> tuple[str, dict]
def answer_dot(question, task_id, run_id) -> tuple[str, list[SubtaskResult]]
```

**`direct` 模式**：跳过 ①②④，`tier = allocator.allocate_one(question)` 做**整请求**判定，
然后 `call_llm(role="executor", tier=..., strategy="direct")` 一次答完。
> 这就是 DataShunt 式的对照臂。**必须注释说明这是规则路由、不是训练出来的路由器**，
> 否则报告里会把它当成强基线。

**`dot` 模式**：`planner.decompose` → `allocator.allocate` → `runner.run` → `aggregator.aggregate`。

**每个请求结束必须**：
1. 用 `time.perf_counter()` 量 `total_ms`（收到请求 → 最终结果返回，**含本地推理**）；
2. 由本次 `task_id` 从库中汇总 `cloud_tokens`（`SELECT SUM(cloud_tokens) FROM calls WHERE task_id=?`，
   注意**含被降级前的失败尝试**）——**不要自己加**，让数据库算，避免漏算；
3. `metrics.record_task(TaskRecord(...))` 落一行，`n_subtasks`/`n_local` 由结果列表统计；
   `direct` 模式 `n_subtasks=0, n_local=0`。
4. 落库用**同一个** `task_id`，这是把整条链路捞出来的主键。

**交互模式**：`rich` 打印；多轮对话历史用**最简单滑窗**（保留最近 N 轮，N=3，常量可改）。
流式输出走 `call_llm(stream=True, on_delta=...)`，`Ctrl+C` 要干净退出（捕获 `KeyboardInterrupt`，
不打印 traceback）。**流式下 token 一律以 usage 为准**（`content` 可能长期为空）。

**`--stats` 看板**（用 `rich.table`）：
- 表 1 请求级对照：strategy / n / p50 / p95 / 云端token合计 / SLM使用率 / 子任务中位数
- 表 2 规划开销单独一块：分解+汇聚的 token 与耗时 **vs** 执行的 token 与耗时
- 表 3 按 role×tier 的调用明细，含 `fallback_calls`（被降级次数）
- 末尾打印**降级提示**：若 `cloud_ready()` 为假，明确写「云端未接入，本表数字为本地降级运行，不代表真实对照结论」

**Windows**：入口处 `sys.stdout.reconfigure(encoding="utf-8", errors="replace")`，
否则中文在 GBK 控制台会乱码。

## 3. 数据流

```
用户请求
  └─ task_id = uuid4().hex[:12]        ← 一次请求内所有调用共享
       ├─ call_llm(role=decomposer, tier=cloud)    ┐
       ├─ call_llm(role=executor,   tier=local)    ├─ 全部写入 calls 表
       ├─ call_llm(role=executor,   tier=cloud)    │  （含失败与重试的每一次尝试）
       └─ call_llm(role=aggregator, tier=cloud)    ┘
  └─ metrics.record_task(TaskRecord)   ← 汇总行，写 tasks 表
```

`run_id` 是**实验批次**，CLI 按 `--run-id` 传入；`task_id` 是**请求**。
两个都进库，排查时先按 `run_id` 圈批次，再按 `task_id` 捞链路。

## 5. 实测结论（决定了上面几个「反直觉」的设计）

| 结论 | 数据 | 影响 |
|---|---|---|
| **`num_ctx` 拐点在 16384** | 4096/8192/12288/16384 均 ~71 tok/s；24576 → 21；32768 → **10.7** | `LOCAL_NUM_CTX` 从计划书的 32768 下调为 16384 |
| **sm_120 冷加载偶发 CUDA 初始化失败** | `server.log`: Load failed → 下一次加载成功 | `call_llm` 加 `retries`；`warmup` 必须带重试 |
| **litellm `num_ctx`/`think` 必须走顶层 kwargs** | 顶层 → `options` 完整；`extra_body` → **options 被整体替换**，temperature/seed 丢失 | 见 `notes/_probe_litellm_body.py` |
| **中文场景 few-shot 必须重写** | 计划书实测 3B 会产出「复述题干」的伪子任务 | planner 的提示词与示例全部重写为中文 |
| litellm 拉远端价格表会因 SSL 卡 4~8 秒 | 本机证书链不全 | `LITELLM_LOCAL_MODEL_COST_MAP=True`，import 降到 2.4s |
| **`stream=True` 必须真的传进 litellm kwargs** | 只加 `stream_options` 而不设 `stream`，litellm 发的是非流式请求，返回 `ModelResponse`；对它迭代拿到 tuple → `chunk.choices` 抛 AttributeError | 流式曾整体不可用；`call_llm` 里 `kwargs["stream"]=True` 是必需的 |
| **中断也占 token** | `KeyboardInterrupt` 继承 `BaseException`，`except Exception` 接不住 → 流式中途 Ctrl+C 时调用完全不落库 | `call_llm` 单列 `except KeyboardInterrupt` 分支：先落库再 `raise` |
| **`_stream_call` 要逐片写回 `result.text`** | 只在循环结束后 join 的话，中途异常时 `result.text` 仍是空 → 「已吐字就不重试」的守卫是死代码，重试会整段重发 | 逐片 `result.text += piece` |
| 云/端的分词器口径不同 | `runner` 的 `fixed_overhead` 若取自一次云端调用，会把云端 token 定义带进本地预算 | 只在 `res.tier == "local"` 的调用上取该常数 |
