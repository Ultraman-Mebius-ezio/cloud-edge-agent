日期：2026-10-11 ｜ run_id：`exp-20261011` ｜ 数据：`runs/metrics.db`

## 一、结论摘要

在同一批题目上对比两种模式（n = 27 次请求 / 每种模式）：

| 指标 | direct（整请求路由） | dot（子任务级分配） | 比值 |
|---|---|---|---|
| **云端 token 消耗** | 2,598 | 110,929 | **42.7×** |
| **任务性能**（7 道计分题 ×3 轮） | 85.7%（18/21） | 100%（21/21） | +14.3pp |
| **完整响应时间** p50 | 624.1 ms | 4,597.2 ms | **7.4×** |
| **完整响应时间** p95 | 5,565.0 ms | 73,346.1 ms | **13.2×** |
| SLM 使用率（分配器判定） | — | 83.2% | — |
| 子任务数中位数 | 0 | 4 | — |

**一句话**：在当前配置下，dot 用 **42.7 倍**的云端 token 和 **7.4 倍的响应时间**，换来准确率 **+14.3pp**。收益与代价严重不成比例。

> ⚠️ 准确率差异**只来自 1 道题**（direct 连续 3 轮都算错「45 人班 3/5 女生」），7 道题的样本量下**不具统计显著性**，不能据此说 dot 更准。

## 三、关键结构性发现

### 3.1 dot 存在一笔与题目难度无关的固定规划税

逐题拆解（每种模式 3 轮的中位数）：

| 题目 | direct p50 | dot p50 | direct token | dot token | 子任务数 |
|---|---:|---:|---:|---:|---:|
| 量化 vs 蒸馏（开放） | 1,982 ms | **64,239 ms** | 323 | **20,456** | 8 |
| 端云协同优势/风险（开放） | 2,617 ms | **70,557 ms** | 455 | **9,347** | 6 |
| 156 ÷ 12 | 134 ms | 12,037 ms | 0 | 1,290 | 5 |
| 37 × 48 | 159 ms | 5,120 ms | 0 | 959 | 4 |
| 18² − 100 | 624 ms | 4,716 ms | 87 | 1,408 | 4 |
| 45 人班 3/5 女生 | 5,586 ms | **3,093 ms** | 0 | 921 | 3 |
| 跑步 3km×5天×4周 | 572 ms | 2,632 ms | 0 | 885 | 2 |
| 24 个苹果吃掉 7 个 | 205 ms | 2,563 ms | 0 | 865 | 3 |
| 320 元打八折再减 20 | 1,495 ms | 2,378 ms | 0 | 842 | 2 |

**「24 个苹果吃掉 7 个」是最能说明问题的一行**：一句话算术题，direct 205 ms / **0** 云端 token，dot 2,563 ms / **865** token——后者全部是分解与汇聚的开销。

**即使最"省"的一次 dot 请求也要 842 云端 token**，而这道题 direct 一个 token 都不用。这笔税不随题目变化，**只随"是否进入流水线"变化**。

### 3.2 规划开销占了 dot 云端 token 的一半

| 项目 | 云端 token | 调用次数 | 耗时合计 |
|---|---:|---:|---:|
| 规划（分解 + 汇聚） | **53,736**（48.4%） | 54 | 64.9 s |
| └ 分解 `decomposer` | 17,296 | 27 | 25.5 s |
| └ 汇聚 `aggregator` | **36,440**（32.9%） | 27 | 39.3 s |
| 执行（子任务） | 57,193 | 134 | 463.9 s |

**汇聚单独一项就占掉全部云端 token 的 32.9%**——因为它的 prompt 要装下所有子任务的答案，而本地子任务在开放题上动辄输出 600–1000 token。这是 DoT 论文未计量的部分。

### 3.3 dot 的代价与题目难度几乎无关，收益却只出现在 direct 失败的题上

- 简单题：dot 纯亏损，token 高 10–30 倍、延迟高 10–90 倍；
- 开放题：dot **灾难性**（64–70 s、9k–20k token），因为被拆成 6–8 个子任务且多数在本地跑、输出极长；
- 唯一 dot 反超的「45 人班」题：direct 本地推理慢（5,586 ms）且**连续 3 轮都算错**，dot 拆解后 3,093 ms 且答对。

**净效果**：dot 目前只在「direct 本身失败或极慢」的少数情形下有价值。根因是 **v4 砍掉了预路由闸门**——所有请求无条件进入流水线，简单题也要付全额规划税。

## 四、局限

1. **样本量小**：9 题（7 题计分）× 3 轮。准确率差异来自 1 道题，**不足以支撑「dot 更准」的结论**，只能作为现象记录。
2. **模型规模远小于论文**：本机 8GB 显存只能用 3B，DoT 论文用 Llama 3-8B。分解质量与子任务粒度的差异直接受此影响。
3. **无依赖图与并行执行**：DoT 的 66% 延迟降幅主要来自图并行，本项目未实现该机制，**不能引用论文的延迟数字**。
4. **分配器是阈值规则**，不是论文的 α-tree 训练 adapter；论文中不训练时 P3 仅 15% 量级。
5. **开放题无法自动评分**，2 道开放题（正是 dot 表现最差的题）被排除在准确率之外——这会让 dot 的准确率数字偏乐观。

---

## 五、结论与下一步

**结论**：子任务级分配本身没有被证伪，但**在当前无闸门的实现下是净亏损**。数据支持三条明确的改进方向：

1. **补预路由闸门（最高优先级）**。3.1 的固定规划税证明：让「24 个苹果吃掉 7 个」进入流水线，代价是 865 token / 2.4 秒，收益为零。闸门只需拦住单步题，就能消掉大部分亏损。
2. **给汇聚瘦身**。它占 32.9% 的云端 token，而输入是本地子任务的长输出——子任务 prompt 应当约束输出长度（如「只给结论，不要过程」）。
3. **收紧分解粒度**。开放题被拆成 6–8 个子任务且多数下沉本地，是延迟 60 s+ 的直接原因。分解 prompt 需要按「子任务必须可独立、简短作答」约束，而不是越多越好。
