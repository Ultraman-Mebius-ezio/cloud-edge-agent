# 端云协同原型 · 计算器工具实验报告 v5

日期：2026-10-12 ｜ 新增 run_id：`exp8`~`exp13` ｜ 前作：v1–v4

> **一句话结论**：给子任务执行器挂上计算器后，dot 第一次同时做到
> **云端 token 低于纯云端（0.60×）** 与 **准确率接近基线（93.3% vs 100%，只差 1 道题）**；
> 但**延迟涨到 20.7 倍**，代价出在 Ollama 一侧，不在我们的代码。
> **仍然不是可用优势**，但差距第一次收敛到「只差一个可定位的工程问题」。

---

## 一、动机：一个精确到个位数的失败

v4 的结论曾是「瓶颈是本地模型能力」。本轮先换了 `qwen3:8b` 去验证这句话——
**结果证伪了它**：8B 与 3B 的端到端准确率几乎无差别（本地规划 73.3% vs 75.6%）。

于是逐条追子任务链，追到了真正的原因。以「油桶」题为例（分解完全正确）：

```
1. 倒掉的一半油 = 25 − 14   → '11千克'  ✓
2. 整桶油 = 11 × 2          → '22千克'  ✓
3. 桶重 = 25 − 22           → '1千克'   ✗   正确答案是 3
```

**分解对、推理链对，栽在一次一位数减法上。** 同类失败还有：

| 题 | 本地给出 | 正确 | 错误类型 |
|---|---|---|---|
| 往返均速 | 75 km/h | 72 km/h | 平均的平均 |
| 长方形面积 | — | 44 cm² | 边长各加 2 的展开 |

这不是模型能力问题——**LLM 的算术滑动在任何参数量上都会发生**，换成 8B 也一样。
所以正确的修复不是更大的模型，而是**把算术从模型手里拿走**。

## 二、新增：计算器工具（三处，其中两处是真实 bug）

### 2.1 `src/tools.py` —— 安全求值

`ast` 白名单求值，只允许数字与四则/幂/取模，**绝不用 `eval`**。
附带全角→半角归一化（中文输入法下模型常输出全角减号）。
自测覆盖了三个卡住模型的算式，全部正确：

```
'25-22'      → 3        (25-14)*2  → 22      360*2/(6+4) → 72
'14*10-12*8' → 44       '２５－２２' → 3        '1/0' → 计算失败：除数为零
'import os'  → 计算失败（不是合法算术表达式）
```

### 2.2 工具循环（`src/runner.py`）

子任务执行时挂上工具，模型回 `tool_calls` 就本地求值、回灌、再问一轮，上限 `MAX_TOOL_ROUNDS=2`。
**每一轮都走 `call_llm`**（申请书要求累计所有 API 调用含重试），工具轮不例外。

### 2.3 途中修掉的两个真 bug

**Bug 1：litellm 的 `ollama_chat` 对本机模型不做原生工具调用。**

实测四种参数组合（最小参数 / +temperature+seed / +num_ctx+think / +max_tokens）
**`tool_calls` 恒为空**，而直连 Ollama 的 `/api/chat` 一次就返回了 calculator 调用。
litellm 内部是靠 `"tools" in template` 判断是否支持原生工具调用的，本机判成了否。

→ 在 `llm_client.call_llm` 内新增一条**直连 `/api/chat` 的通道**，仅用于「本地 + 带工具」。
**仍然在唯一调用出口内部**，落库、重试、降级逻辑一行未改。

**Bug 2：Ollama 要 `arguments` 是对象，OpenAI/litellm 要字符串。**

内部统一按 OpenAI 形状存（litellm 路径产出的就是字符串），直接回灌给 Ollama 会 400：

```
{"error":"Value looks like object, but can't find closing '}' symbol"}
```

这个错误**不含字段名**，靠对字段二分才定位到。修复方式是在发往 Ollama 的那一层
做转换（`_to_ollama_messages`），而不是在内部改表示。同时在原生通道里把 HTTP 错误的
**响应体读出来**——否则这类问题只会显示一个 `400`，无法排查。

## 三、结果

17 题 × 3 轮 = 51 请求/臂；计分 15 题。纯云端基线约 6,300~6,500 token、100%、约 700~820 ms。

| 模型 | 工具 | 规划链 | dot 云端token | 纯云端 | 相对 | dot 准确率 | dot p50 |
|:--|:--:|:--|--:|--:|--:|--:|--:|
| 3B | ✗ | 本地+本地 | 2,848 | 6,315 | 0.45× | 75.6% | 2,318 ms |
| 3B | ✗ | 本地+云端 | 12,051 | 6,297 | 1.91× | 86.7% | 2,482 ms |
| 3B | ✗ | 云端+云端 | 34,675 | 6,551 | 5.29× | 100% | 2,137 ms |
| 8B | ✗ | 本地+本地 | 2,900 | 6,322 | 0.46× | 73.3% | 2,608 ms |
| 8B | ✗ | 本地+云端 | 11,401 | 6,303 | 1.81× | 86.7% | 2,838 ms |
| 8B | ✗ | 云端+云端 | 34,410 | 6,382 | 5.39× | 86.7% | 2,131 ms |
| **8B** | **✓** | **本地+本地** | **3,894** | **6,469** | **0.60×** | **93.3%** | 16,936 ms |
| 8B | ✓ | 本地+云端 | 12,564 | 6,254 | 2.01× | 93.3% | 16,226 ms |
| 8B | ✓ | 云端+云端 | 35,340 | 6,366 | 5.55× | 95.6% | 14,641 ms |

### 3.1 工具显著提准确率，且几乎不花云端 token

| 配置 | 无工具 | 有工具 | 变化 |
|:--|--:|--:|:--|
| 8B · 规划全本地 | 73.3% | **93.3%** | **+20.0pp** |
| 8B · 分解本地+汇聚云端 | 86.7% | 93.3% | +6.6pp |
| 8B · 规划全云端 | 86.7% | 95.6% | +8.9pp |

云端 token 几乎不变（本地规划 2,900 → 3,894，仅 +34%；其余两格基本持平）——
因为**计算器在本地求值，不产生云端 token**。这正是它同时改善准确率与指标一的原因。

误差只剩 **1 道题**（「仓库 500 箱」，3 轮全错）。

### 3.2 代价：延迟涨到 20.7 倍，且原因在 Ollama 一侧

同一运行内可比：dot p50 **16,936 ms** vs 纯云端 **819 ms**。

拆开看是**每一次本地调用都变慢**，不是长尾：

| | 无工具 | 有工具 |
|:--|--:|--:|
| 本地调用数 | 201 | 285 |
| 本地耗时合计 | 100 s | **710 s** |
| 单次延迟 p10 | 109 ms | **1,806 ms** |
| 单次延迟 p50 | 163 ms | **2,192 ms** |
| 平均输出 token | 22 | 22（相同） |

输出长度完全一样，延迟却涨了一个数量级。

**机制（微基准验证）**：用一个 30 token 的短 prompt 对比，带 tools 只慢 1.14 倍
（97.6 → 60.9 tok/s，预填 34 ms）。而流水线里的 prompt 约 400 token，
带 tools 时每次都要**全量预填约 2 秒**。

→ **带 `tools` 时 Ollama 失去前缀缓存，每次调用重新预填**；prompt 越长，惩罚越重。
这不是我们的代码问题，是 Ollama 在工具模式下的一侧行为。

## 四、诚实的结论

按「准确率接近基线的前提下降低云端 token」逐条核对：

| 指标 | dot（8B · 工具 · 规划全本地） | 纯云端 | 判定 |
|:--|--:|--:|:--|
| 云端 token | 3,894 | 6,469 | ✅ **低 40%** |
| 任务性能 | 93.3%（14/15 题） | 100% | ⚠️ 差 6.7pp（1 道题） |
| 完整响应时间 p50 | 16,936 ms | 819 ms | ❌ **高 20.7 倍** |

**两项改善、一项崩掉，仍不构成可用优势。**

但与前几轮不同的是：**这轮的差距第一次收敛到一个可定位、且不在我们代码里的工程问题**——
Ollama 在带 tools 时丢失前缀缓存。前三轮的失败是结构性的（context 重发、规划税），
这一轮是单点性能问题。

**同时证伪了一个之前的判断**：v4 说「瓶颈是本地模型能力」，换 8B 实测**不成立**。
真正的瓶颈是**算术可靠性**（换模型无用，工具才有用）与**调用次数**。

## 五、下一步（按可能性排序）

1. **绕开 Ollama 的工具模式开销**。既然带 `tools` 就丢前缀缓存，可以不走工具协议：
   让子任务先输出算式（文本协议），由 runner 本地求值后回灌。**收益直接**——
   保住 +20pp 准确率，同时把本地延迟降回 2.5 秒量级。这一步最可能把三项指标同时做正。
2. **减少本地调用次数**。285 次本地调用是延迟的主因。闸门已拦掉一部分，
   但规划链本身（分解 + 汇聚各 1 次）与子任务数仍可压。
3. **把长上下文场景补回来**。本机 8GB 显存装 8B（5.2GB）后 `num_ctx` 只能到 8192
   （12288 就掉到 13% CPU），装不下 13k 字的长上下文，**该场景本轮无法测**。
   需要实验室 16GB 机。

**不建议继续做的**：继续换更大的本地模型——本轮已实测 3B → 8B 无改善。

---

## 六、局限

1. **本地模型 qwen3:8b 受显存限制，`num_ctx` 从 16384 降到 8192**。3B 与 8B 的对比因此
   不是纯模型差异，也含窗口差异（但已核查失败题的 prompt 仅约 100~200 token，未触及预算）。
2. **样本小**：15 道计分题 × 3 轮。93.3% 与 100% 的差距是 1 道题。
3. **长上下文场景缺测**（见上）。
4. **p95 噪声大**：同配置两次运行 p95 可差 47%（v2 第 6 节）。本报告以 p50 与 token 为主。
5. **口径**：`cloud_tokens` 含 DeepSeek 前缀缓存命中部分；「消耗」与「计费」是两个量（待补双口径）。
6. 分配器仍是阈值规则，非 α-tree adapter。
